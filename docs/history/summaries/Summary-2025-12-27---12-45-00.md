## Fonctionnalités implémentées

### 1. Initialisation dans `boot()`

Le contexte DataMapper est initialisé au démarrage du bundle pour que les data objects aient accès au Loader. Cette approche permet de coupler faiblement les data objects avec le loader tout en les conservant sérialisables.

```php
class KasskoDataMapperBundle extends Bundle
{
    public function boot(): void
    {
        $this->initDataMapper();
    }

    private function initDataMapper(): void
    {
        $this->container->get('kassko_data_mapper.data_mapper');
    }
}
```

### 2. Injection de dépendances

- **ServiceResolver** : Intégration avec le container Symfony pour résoudre les services
- **Cache** : Support PSR-16 configurable
- **Logger** : Support PSR-3 avec canal Monolog configurable

### 3. Data Lineage Profiler

Panneau dans le Web Profiler Symfony avec:
- **Timeline des événements** : Vue chronologique des opérations de données
- **Groupement par classe** : Événements organisés par classe d'objet
- **Groupement par type** : Événements organisés par type d'opération
- **Statistiques** :
  - Nombre total d'événements
  - Appels DataSource
  - Hydrations de propriétés
  - Propriétés ignorées (avec raisons)
  - Profondeur maximale d'hydration
  - Durée totale

### 4. Commandes console intégrées

```bash
# Valider une classe spécifique
php bin/console datamapper:validate:class 'App\Entity\User'

# Valider toutes les classes d'un répertoire
php bin/console datamapper:validate src/Entity --namespace='App\Entity'
```

### 5. Configuration flexible

```yaml
# config/packages/kassko_data_mapper.yaml
kassko_data_mapper:
    enable_lineage_collection: false  # Activer la collecte du lineage
    enable_profiler: true              # Activer l'intégration profiler
    
    cache:
        enabled: false
        service: null                  # Service PSR-16 (ex: 'cache.app')
    
    logger:
        enabled: true
        service: 'logger'              # Service PSR-3
        channel: 'data_mapper'         # Canal Monolog
    
    validation:
        paths: []                      # Chemins à scanner
        namespaces: []                 # Namespaces pour résolution
```

## Points clés de l'architecture

1. **Découplage** : Les data objects restent sérialisables sans dépendance directe sur le Loader
2. **Initialisation paresseuse** : Le contexte est créé au boot du bundle
3. **Intégration native Symfony** : Utilisation des standards (DI, Configuration, DataCollector)
4. **Extensibilité** : Configuration flexible via YAML
5. **Debugging** : Profiler complet pour tracer le flux de données
